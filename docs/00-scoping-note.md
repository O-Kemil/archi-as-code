# Scoping note: application inventory as code

*Demonstration scenario for this project (fictional context)*

## Context

Maison Zola is a ready-to-wear fashion retailer with around 150 stores and an e-commerce site. Its IT landscape counts about sixty applications (point of sale, inventory, logistics, e-commerce, finance, HR, data). The IT department has no commercial enterprise architecture tool (such as LeanIX), which was considered too expensive for its size. The existing application map is an Excel workbook and a few Visio diagrams, updated by hand, with no identified owner.

## Trigger

The hosting contract for the main data center ends in 18 months and will not be renewed. The IT department has until then to migrate or decommission every hosted application.

## Problem statement

Information about the IT landscape is scattered across an Excel workbook, Visio diagrams, project documents and people's memory. None of these sources is authoritative and they contradict each other. As a result, nobody can reliably say which applications depend on each other, which ones run on end-of-life technologies, or who makes decisions for each of them. As long as these questions stay unanswered, the migration cannot be split into waves and its risk cannot be estimated.

## Needs

- A single, up-to-date inventory where every change is tracked and reviewed.
- A dependency map that is regenerated automatically.
- An anomaly report listing end-of-life technologies, applications without an owner and circular dependencies.
- An export that can be used in Archi, the team's modeling tool.

## Scope of v1

- YAML inventory, one file per application, validated by a Pydantic schema.
- Dependency graph built with NetworkX, exported to Mermaid and Graphviz.
- Automatically generated Markdown report.
- Export to the Archi exchange format.
- GitHub Actions: validation on every push, failure if the inventory is invalid, regeneration of the deliverables.

## Out of scope

- Automatic discovery (network scans, CMDB, agents).
- Web interface, database, access rights management.
- Detailed infrastructure (servers, networks), fine-grained data flows, costs.
- The migration plan. The tool provides the inputs needed to build it.

## Stakeholders

| Role | Expectation |
|---|---|
| CIO (sponsor) | View of the migration's risk and progress |
| Enterprise architect (project lead) | Reliable repository, up-to-date maps |
| Application owners | Simple update of their record through a pull request |
| CISO | List of end-of-life technologies |
| Migration project manager | Dependencies to split the migration into waves |

## Success criteria

- 60 application records that are valid against the schema.
- An invalid record makes the CI fail, with an error message naming the file and the field.
- The map and the report are regenerated with no manual action.
- The report detects the anomalies deliberately placed in the dataset (at least one of each type).
- The export opens in Archi without errors.

## Constraints

- Git is the only source of truth, with no database.
- Python and open source tools only, no real company data.
- Every structuring decision is recorded in an ADR under `docs/adr/`.

## Framing and limits of the demonstration

This project is a personal learning exercise, carried out alone alongside a work-study position and a master's degree. It does not try to compete with commercial enterprise architecture tools. It targets organizations that do not have one, and it helps understand the building blocks these tools rely on.

The record model is inspired by the public LeanIX metamodel (application, IT component, lifecycle, business criticality).

In a real situation, each record would be written and maintained by the application owner. Here, about fifteen applications and their IT components are curated, that is designed and checked one by one, and the others are generated by a script, for lack of time.

Beyond a few dozen non-technical contributors, with per-domain access rights and approval workflows, a commercial tool becomes the right choice.
