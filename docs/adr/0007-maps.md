# ADR-0007: Maps, content, views and formats

- Status: Accepted
- Date: 2026-10-14
- Deciders: Kemil

## Context

The scoping note asks for a dependency map regenerated automatically, exported to Mermaid and Graphviz. The graph of ADR-0005 holds applications, IT components and typed edges; the report of ADR-0006 computes the anomalies. This ADR decides what a map shows, which views exist, how the two formats are used and produced. The Archi export is a separate decision.

Facts verified on 2026-10-14:

- GitHub renders Mermaid diagrams written in a ```` ```mermaid ```` fenced block in Markdown files, issues, pull requests, discussions and wikis (GitHub Docs, "Creating diagrams"). The GitHub blog post announcing job summaries (2022-05-09) says they support GitHub Flavored Markdown and names Mermaid; the documentation page does not list job summaries explicitly, so the rendering on the run page had to be confirmed by the first CI run. Confirmed on 2026-10-15: the hosting view is rendered as a diagram in the job summary.
- Mermaid flowcharts support a label on a link (`A -->|api, file| B`), grouping (`subgraph ... end`) and styling by class (`classDef`, `class`); special characters go in quoted labels (Mermaid documentation, flowchart syntax).
- DOT identifiers are letters, digits and underscores, or any string in double quotes; an edge takes attributes (`A -> B [label="api"]`); a subgraph named `cluster...` is drawn as a box (Graphviz, "The DOT Language").
- The `ubuntu-24.04` runner image does not include Graphviz; the documented installation on Ubuntu is `apt install graphviz` (Graphviz download page). The Python packages `graphviz` and `pydot` are interfaces that call the `dot` binary; they do not render by themselves.

## Decision drivers

- D1. A reader on GitHub sees a map without installing anything.
- D2. The complete map of 60 applications stays usable, zoomable.
- D3. The visual conventions are stable: the same sign means the same thing in every map and every version.
- D4. Deterministic output (ADR-0005, D2) and the generated-deliverables path of ADR-0006.
- D5. No dependency or schema change without a demonstrated need.

## Options considered

### Nodes of the global map

- A: applications only. The dependency map of the scoping note; a component shows through the colour of the applications that use it.
- B: applications and components. Shared components become stars that hide the business structure; unreadable at 60 applications.
- C: applications plus the components that are end of life. B filtered: a view, not another content.

### Grouping

- By `hosting`: possible today, and it is the axis of the migration (what is in the data center and what it talks to).
- By domain: no field in the schema. It would need an amendment of ADR-0001 adding `domain` to the application, either a closed enumeration or a slug checked against a reference list in the inventory. Deferred: the hosting and focus views cover the two uses of the scoping note, migration waves and impact; a domain has no requester yet. To reconsider with the 45 generated records.
- By owner: possible today but `business_owner` is free text, so spelling variants would split a group (limit noted in ADR-0001). Rejected.

### Graphviz rendering

- A: DOT file only, no dependency; the reader renders it. Nobody opens a `.dot`.
- B: DOT written by the project, rendered to SVG in the CI by the `dot` binary installed with `apt-get install graphviz`. No Python dependency.
- C: the `graphviz` or `pydot` package. Needs the binary anyway; an object API to save thirty lines of f-strings. Rejected.

## Decision

1. Roles of the formats. Mermaid is for reading inside GitHub without any tool, on the run page and in Markdown; it is limited to about twenty nodes, beyond which it renders but cannot be read. Graphviz is for the complete map, zoomable as SVG; it requires the `dot` binary. Each view is produced in both formats; the Mermaid output of the global view exists for completeness and is not shown on the run page.
2. Content. The global map shows applications only (option A). One arrow per pair of applications in the declared direction, labelled with the dependency types in enumeration order (`api, file`). Node labels are the record names; node identifiers are the record ids, written with underscores in Mermaid because hyphens and some words have a meaning in its syntax, and quoted in DOT. Nodes and arrows are emitted sorted by id.
3. Visual conventions (D3). An application without business owner has a dashed border. An application running on a component past end of life on the reference date has a light red fill; running on a component reaching end of life on or before the deadline, a light orange fill, when a deadline is given; red wins over orange. Cycles have no sign: they are visible and listed in the report. Each SVG carries a legend cluster; the Mermaid view on the run page is followed by a one-line legend in the summary. `archinv map` therefore takes `--reference-date` and `--deadline` like `archinv report`.
4. Views of v1: `global` (applications only); `hosting` (one box per `hosting` value, applications inside, arrows between boxes); `focus` on one application (itself, its direct dependents and its direct dependencies, `--focus ID`); `end-of-life` (option C: the components that are past end of life or before the deadline, as cylinders, with the applications using them). The CI produces `global`, `hosting` and `end-of-life`; `focus` is produced on demand. The `focus` view is the induced subgraph: every edge between the selected applications is shown, not only those touching the focus, so that a cycle closing between two neighbours stays visible. In the `end-of-life` view the nodes are the applications first, then the components, each group sorted by id: a deliberate exception to the strict sort by id, so that a renderer can draw the two kinds apart without sorting again.
5. Command: `archinv map --format {mermaid,dot} --view {global,hosting,focus,end-of-life} [--focus ID] [--reference-date] [--deadline] [--output PATH]`, one file per call, stdout by default, `.mmd` and `.dot` extensions by convention. Same statuses as `report`: 0, or 1 on an invalid inventory.
6. Graphviz, option B. The workflow installs Graphviz with `apt-get install graphviz` and renders each DOT file to SVG with `dot -Tsvg`. This is the one unpinned installation of the workflow: the apt package follows the Ubuntu 24.04 release and only receives security updates; pinning an exact apt version would break at the first of them. The exception is accepted and written here. Confirmed on 2026-10-15: the apt step and the SVG rendering pass in the CI, and the three SVG files are in the artifact.
7. Tests compare text only: the DOT and Mermaid outputs against expected strings, on in-memory inventories and on the curated data set. The SVG rendering is verified only by the CI step, which fails if `dot` rejects a file. Graphviz is optional on a laptop.
8. The run page shows the `hosting` view as a Mermaid block; `generated/` with every `.mmd`, `.dot` and `.svg` goes into the artifact of ADR-0006. One dated example is committed, the `hosting` view as SVG under `docs/`, used as the image of the README.

## Consequences

- Positive: a map readable on GitHub with no tool, a complete zoomable map in the artifact, the migration axis (hosting) and the impact view (focus) available from the existing schema, end-of-life exposure visible at a glance, conventions a reader can learn once.
- Negative: the global Mermaid map is unreadable at 60 applications and exists only for completeness; the SVG rendering is not covered by tests; one apt installation is not pinned; the focus view is not produced by the CI, so it is not in the artifact.
- Follow-up: a `domain` field (amendment of ADR-0001) if grouping by hosting proves insufficient with the generated records; the focus view for every application and the maps at a stable address with the published site of v1.1; the Archi export, with its own ADR on the ArchiMate mapping.
