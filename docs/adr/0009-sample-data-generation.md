# ADR-0009: Sample data generation

- Status: Accepted
- Date: 2026-10-16
- Deciders: Kemil

## Context

The scoping note sets a success criterion of 60 valid application records and says that about fifteen are curated and the others generated by a script. The curated data set has 15 applications and 9 IT components (ADR-0001 conventions, acceptance list of expected anomalies). The report (ADR-0006), the maps (ADR-0007) and the Archi export (ADR-0008) are tested against that list. The generator must add 45 applications without changing what the report finds, except for anomalies chosen on purpose.

Facts verified on 2026-10-16: the Python `random` module guarantees that `random()` yields the same sequence for the same seed across versions, but not `choice()`, `shuffle()` or `sample()`, which may change between Python versions. The project pins Python 3.13 (`.python-version`, ADR-0002).

## Decision drivers

- D1. 60 applications that read like a fashion retailer's landscape, connected mostly to the existing pivots.
- D2. The report finds exactly the acceptance list, plus the anomalies added on purpose, nothing else.
- D3. The same output at every run, so that a regeneration shows no diff unless the script changed.
- D4. The complete data set is in the repository: a clone, a local Archi import and the CI see the same inventory.

## Options considered

### How the records are produced

- A: everything drawn from archetypes. Little to write, implausible names and links, anomalies hard to control.
- B: 45 complete records listed in the script. No randomness, but 45 more curated records, which the scoping note says there is no time for.
- C: a hand-written table of 45 applications (id, name, domain, hosting) and seeded rules for the rest: targets among the pivots of the domain, link types, components by hosting, lifecycle dates in fixed ranges per domain. Judgement is written, chores are drawn.

### Where the generated records live

- Committed under `inventory/`, like the curated ones, with a header comment, and a CI step that regenerates and fails on any diff.
- Produced by the CI at run time: the repository holds 24 records, the CI deliverables show 69, a clone and a local Archi import differ from the CI, the acceptance test cannot run locally without regenerating. Rejected (D4).

This differs from ADR-0006, where `generated/` is produced by the CI and never committed, for two reasons that do not hold here: the deliverables depend on the date of the day, while the generated records contain no date relative to today, so a regeneration is stable; and a deliverable is produced for its readers, while a record belongs to an application owner who edits it, except that generated records belong to nobody and are edited through the script only.

## Decision

1. Option C. Six domains with their pivots: store operations (pos-stores, store-inventory, product-catalog); supply chain (warehouse-management, store-inventory, erp-finance, product-catalog); e-commerce and marketing (ecommerce-site, order-management, product-catalog, loyalty-crm); finance and corporate (erp-finance); HR (hr-payroll); data and IT (data-warehouse, bi-reporting, some applications with no dependency). About two thirds of the links go to pivots, the rest to a generated application of the same domain. The declaring side is always the generated application: the curated records do not change.
2. Four curated IT components are added for the generated applications, all with an end of life after the data set deadline (2028-03-31), with vendor sources in their header like the first nine: `postgresql-16`, `red-hat-enterprise-linux-9`, `windows-server-2022`, `sql-server-2022`. Generated applications run on components that are not end of life, except where decision 4 says otherwise.
3. Anomalies by construction. Every generated application has a business owner (the team of its domain). Each generated application has a rank and depends only on curated pivots or on generated applications of a lower rank, so no new cycle can appear. Targets are distinct and no generated application declares two links to the same target, so the only double link stays `supplier-portal` to `erp-finance`. A `saas` application has no component; any other has at least one.
4. Anomalies on purpose, in one explicit list `EXTRA_ANOMALIES` in the script, not empty from the start so that the mechanism is exercised: two store operations applications run on `windows-server-2012-r2` (more applications on a component already listed as end of life: the component list of the report does not change, its "applications using it" column grows), and one data and IT application has no business owner. No new cycle, no new double link, no new end-of-life component. The acceptance list in `CLAUDE.md`, `tests/test_dataset.py` and `EXTRA_ANOMALIES` change together, in the same commit.
5. Reproducibility: `random.Random` with a fixed seed, iteration over sorted lists, lifecycle dates drawn in constant ranges, nothing relative to today. The output is identical at every run on Python 3.13; if a Python upgrade changes `choice()` or `shuffle()`, the records are regenerated and committed, and the diff is reviewed.
6. The script `scripts/generate_sample_inventory.py`, run with `uv run python scripts/generate_sample_inventory.py`, removes the previously generated files (recognised by their header, never the curated ones), writes the new ones into `inventory/applications/`, and validates the whole inventory with the loader before returning; on a validation error the files stay in place for inspection and the script exits with status 1. Every generated file starts with `# Generated by scripts/generate_sample_inventory.py: do not edit, change the script and run it again.` and `# Domain: <domain>`.
7. The CI regenerates the records after the validation step and fails if `git diff --exit-code inventory/` shows a change: a generated record edited by hand, or a script changed without regenerating.
8. `tests/test_dataset.py` is the acceptance test of the complete data set: 60 applications; the applications without business owner, the cycles, the components past end of life on 2026-10-16 and before 2028-03-31, exactly as listed in `CLAUDE.md`; no application without component outside SaaS. `docs/report-example.md` is regenerated at 60 applications.
9. The domain is written as a header comment only. Whether a `domain` field enters the schema (amendment of ADR-0001) is decided after looking at the maps at 60 applications: the global map, the hosting view with about 35 applications in the data center box, and the job summary.

## Consequences

- Positive: the scoping note's 60 records, a realistic landscape centred on the pivots, the anomaly list under control by construction and by test, a data set that is the same everywhere, generated records that cannot drift from the script.
- Negative: 45 more files in the repository; one more CI step; the "script first" discipline for generated records; the lifecycle dates of generated applications are plausible, not researched; the domain information exists only in comments until the schema carries it.
- Follow-up: the `domain` field and a domain view if the maps at 60 call for it; a headless Archi import of the 69-record model; the job summary may need to show only the data center box.
