# archinv v1.0.0: application inventory as code

Released 2026-10-16.

A small tool that keeps an application inventory in Git, validates it on every change, and generates a dependency map, an anomaly report and an ArchiMate export from it. A personal learning project with an architect's posture: every structuring decision is an ADR, and the sample data set is a fictional fashion retailer, Maison Zola, leaving its data center within 18 months.

## What it does

- `archinv validate` loads `inventory/` (one YAML file per application and per IT component, validated by a Pydantic schema), reports every error with the file and the field, and exits with status 1 when the inventory is invalid.
- `archinv report` writes a Markdown anomaly report at a reference date: applications without business owner, circular dependencies, IT components past end of life and those reaching it before a deadline, applications without component, the most depended-upon applications. Anomalies never fail the CI: a valid record that reveals a problem must reach the report.
- `archinv map` writes dependency maps in Mermaid and Graphviz DOT, in four views (global, by hosting, focus on one application, end-of-life exposure), with visual signals for the anomalies.
- `archinv archi` writes the inventory as an ArchiMate Open Exchange Format 3.1 file that Archi imports without plugin.
- GitHub Actions runs all of this on every push, every night and on demand, shows the report and the end-of-life map on the run page, and attaches every deliverable to the run.

## The sample data set

60 applications and 13 IT components. 15 applications and 13 IT components are curated (written and sourced by hand: the end-of-life dates come from the vendors' documentation, cited in each record); 45 applications are generated by `scripts/generate_sample_inventory.py` from a hand-written table and seeded rules, and committed, so that a clone, a local Archi import and the CI see the same inventory.

## The five success criteria of the scoping note

1. **60 application records valid against the schema.** `inventory/applications/` holds 60 records; `archinv validate` prints `Inventory valid: 60 applications, 13 IT components`; `tests/test_dataset.py` checks the count and the CI validates on every push.
2. **An invalid record makes the CI fail, naming the file and the field.** Proven on 2026-10-09 by [CI run #3](https://github.com/O-Kemil/archi-as-code/actions/runs/37916382953) on the branch `test/invalid-record`: `broken.yaml` failed the validation step with `business_criticality: Input should be ...`. The loader and CLI tests cover every kind of error (ADR-0003, ADR-0004).
3. **The map and the report are regenerated with no manual action.** The workflow runs on push, pull request, nightly schedule and manual trigger, shows the report and the end-of-life map on the run page and attaches every deliverable to the run (ADR-0006, ADR-0007).
4. **The report detects the anomalies deliberately placed in the data set.** `tests/test_dataset.py` checks the exact list: three applications without business owner, one cycle, five components past end of life, two reaching it before the deadline, and that there is no application without IT component outside SaaS, the fifth kind of anomaly, none being placed. `docs/report-example.md` is the dated report.
5. **The export opens in Archi without errors.** Export produced on 2026-10-16 with `uv run archinv archi --name "Maison Zola application inventory" --reference-date 2026-10-16 --output generated/inventory.archimate.xml`, imported into an empty model of Archi 5.10.0 without error: 60 Application elements, 13 Technology & Physical elements, 185 relationships, equal to the number of edges of the graph. The export is also validated in the tests against The Open Group XSD and against Archi's relationship matrix (ADR-0008).

## Decisions

Nine ADRs under `docs/adr/`, from the inventory schema (ADR-0001) to the sample data generation (ADR-0009), each with its options, the choice and its cost, dated sources, and clarifications or amendments when coding changed the picture.

## Known limits of v1

- At 60 applications the hosting map is no longer readable: it does not answer the migration question of the scoping note (what leaves the data center and what it talks to). The report and the Archi export cover that question in v1.
- The schema records which application triggers an exchange, not which way the data flows, so every link is exported to Archi as a Serving relationship, never as a Flow.
- `impacted_by` (dependents in cascade) is provided by the graph module but has no consumer in v1, neither the report nor a map; it is kept for the migration map of v1.1.
- A learning exercise, not a product: it suits teams that already work in Git; the sample inventory is fictional.
